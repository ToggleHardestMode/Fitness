# V10.3 Transition Plan — app support for moving from V10.2 to V10.3 (2026-11-05)

**Status:** PLANNED — specification for implementation. Nothing here is built yet.
**Owner decisions it implements:** decisions 2 and 7 in [2026-11-05-roadmap-owner-decisions.md](../decisions/2026-11-05-roadmap-owner-decisions.md).
**Scope:** `preview-v101/` only. Production root is untouched.

## Why this is needed

A source review of main at `9e1d6c8` found that the preview records V10.3 but cannot steer the owner towards it:

| Gap | Current behaviour | Task |
|---|---|---|
| History resets on switch | Strength Journey and both progression functions key history on `templateId` + `exerciseIndex`. Importing V10.3 creates new template IDs, so every exercise starts as "no history". | B073 |
| No volume ramp | `recommendNextExercise` holds with "incomplete working sets" whenever fewer sets than the template's `sets` are logged, so building up towards the 37-set target blocks every suggestion. | B114 |
| Lower body never progresses | Any `[PT Review]` template or `[PT]` exercise returns `pt-review` permanently; there is no way to record that a clinician has cleared a specific movement. | B115 |
| Reset leaves the journey start date | `resetTrackingData` clears logs, metrics and symptom logs but keeps `strengthJourneyStartDate`. | B111 |

Open owner decision, **not** part of this implementation: B116 (scope of general symptom entries). Current behaviour — any general entry with a non-zero finding blocks progression for every exercise that day — must stay unchanged.

## Implementation order

Four separate PRs, in this order, each based on the previous one because B073, B114 and B115 all touch `strength-journey.js`:

1. **B111** — tracking-reset fix (smallest; independent).
2. **B073** — exercise equivalence map.
3. **B114** — active sets.
4. **B115** — per-exercise clearance.

## Rules for every PR

- Follow the conventions of recent preview PRs (#65–#67): bump the preview version label and the service-worker cache name, and add new modules to the service-worker asset list.
- New state fields are **optional**. A backup without them must still validate and restore unchanged; `validateBackup` must reject malformed values with a clear message and never repair input silently.
- Never rewrite, delete or re-key existing `logs`, `metrics` or `symptomLogs`.
- Nothing is inferred or applied automatically. Every new record is created only by an explicit owner action with a confirmation step.
- All existing progression guards stay exactly as they are, except the single change each PR specifies.
- Add focused `node:test` tests under `tests/`, then run the full `npm test`, and report the native result in the PR. Do not claim iPhone or Pages verification.
- No personal training data, health details or credentials in the public repo or test fixtures; use synthetic data only.

## PR 1 — B111: reset clears the journey start date

- `tracking-reset.js`: add `restartDateCleared` (1 if `strengthJourneyStartDate` is present, else 0) to `counts`; in the applied state, remove `strengthJourneyStartDate`.
- Keep templates, assignments, reminder, `progressionStepKg` and every field added by later PRs (`exerciseEquivalences`, `activeSets`, `exerciseClearances`). Those are configuration, not tracking.
- The reset confirmation UI in `app.js` should mention that the Strength Journey start date is cleared.
- Tests: the start date is removed; templates and assignments are deep-equal before and after; a state without the field still resets; preview mode (`apply:false`) changes nothing.

## PR 2 — B073: exercise equivalence map

**State:** optional `exerciseEquivalences`: an array of
`{id, from:{templateId, exerciseIndex}, to:{templateId, exerciseIndex}, approvedDate:"YYYY-MM-DD", note?}`.

**Validation:**
- Both references exist.
- `from` and `to` differ.
- Both have the same `repUnit` (a timed hold can't link to a rep exercise).
- At most one link per `from`, and no cycles. Chains such as V10.1 → V10.2 → V10.3 are allowed.
- `note` is at most 200 characters.
- Unique `id`.

**Behaviour:**
- `getExerciseJourney` also returns sessions from linked earlier exercises, following the chain backwards. Each session carries `source:{templateId, exerciseIndex, exerciseName}` and `linked:true`. The chart shows a visible marker where the exercise changed.
- Progression stays conservative: `recommendNextExercise` and `manualProgression` still base their suggestions **only on sessions of the current exercise**.
  - When there are none, the `no-history` result adds a `reference` field: the latest linked session's date, kg, reps and exercise name.
  - The reason text says it is a reference for choosing a starting weight, not a target.
- Weekly analytics and lifetime counters are unchanged. No log is re-keyed.

**UI:**
- In the exercise view, add a "Link earlier history" action. It lists candidate exercises from other templates; identical names may be listed first, but each link needs its own explicit confirmation.
- Existing links appear in a list with an "Unlink" action (with confirmation). Unlinking removes only the link record.

**Tests:** chain resolution; cycle and duplicate rejection; timed-unit mismatch rejection; no change to `logs`; the `no-history` reference is populated; suggestions are unchanged when current-template sessions exist; the backup round-trips; an old backup without the field validates.

## PR 3 — B114: active sets

**State:** optional `activeSets`: an object keyed `"<templateId>|<exerciseIndex>"`, with whole-number values from 1 to that exercise's `sets`. Keys must reference existing exercises.

**Behaviour:**
- The expected set count for an exercise is `activeSets[key] ?? exercise.sets`.
- In `recommendNextExercise`:
  - The "incomplete working sets" check and the previous-session completeness check compare against the expected count, using sets 1..expected.
  - Logged sets above the expected count are ignored for progression.
  - The rep and load targets returned cover sets 1..expected.
- `manualProgression` is unchanged (it is per set).
- Raising or lowering active sets is manual only. The app never changes it automatically.

**UI:** in Train, show "Doing X of Y planned sets" on each exercise where active < target, with a control to change X (1..Y) and a confirmation step.

**Analytics:** none in this PR. B050 (planned vs actual) stays separate.

**Tests:** progression with active < target holds or proceeds correctly; extra logged sets are ignored; invalid keys and values are rejected; absent field → identical behaviour to today, checked against the existing strength-journey tests.

## PR 4 — B115: per-exercise clinical clearance

**State:** optional `exerciseClearances`: an array of
`{id, templateId, exerciseIndex, clearedDate:"YYYY-MM-DD", clearedBy (1–80 chars), note? (≤200), revokedDate?}`.

**Validation:**
- The reference exists.
- `revokedDate` is on or after `clearedDate`.
- At most one unrevoked clearance per exercise.

**Behaviour:**
- In both `recommendNextExercise` and `manualProgression`, the PT-review early return is skipped **only** for an exercise with an unrevoked clearance dated on or before the workout/review date.
- Every other guard still applies: symptoms, complete observations, recovery score, RPE, technique, difficulty, set completeness and increments.
- The template keeps `requiresClinicalReview`, so automatic weekday assignment still rejects it, and the PT Review banner stays.
- The exercise shows "Cleared by <clearedBy> on <date>" in place of "reference only".
- A clearance never carries across an equivalence link. A new movement needs its own clearance.

**UI:** in a PT-review exercise view, add a "Record clinician clearance" action. The confirmation text must state that the owner is recording a clearance given by a clinician and the app does not verify it. Also add a "Revoke" action.

**Tests:** cleared exercise progresses under normal gates; uncleared and revoked exercises stay `pt-review`; clearance dated after the workout date does not apply; concerning symptoms still block a cleared exercise; equivalence links do not transfer clearance; backup round-trip.

## Not in scope

- B116 symptom-scope change.
- Encrypted backup (B110).
- Analytics or overlap-coefficient changes.
- Production root changes.
- Any automatic linking, ramping or clearance.
