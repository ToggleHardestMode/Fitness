**Status:** Owner approved; phase 1 foundation in this PR, activation deferred. Preview only.

**Authority:** “I explicitly approve the hybrid session architecture and backward-compatible saved-record schema extension for FitnessPilot preview only. Record the dated architecture decision, preserve existing records and owner-approved equivalence and clinical safeguards, and implement the first phase. Do not modify production files or merge before verification.”

This is a scoped dated amendment to the saved-record-shape restriction in [restructure permissions](2026-11-11-roadmap-restructure-permissions.md) and AGENTS §9. It does not authorize a new storage key, production edits, automatic linking, changed clinical/progression gates, or incompatible legacy restore. Decisions 2 and 7 in [owner decisions](2026-11-05-roadmap-owner-decisions.md) remain in force. The rejected historical-template workaround (#139) is not the foundation.

## Contract

- Version 1 remains the only live workout document in phase 1, at the unchanged preview key. Version 2 is a pure validated document: `{version:2, legacy:<unchanged v1 document>, exercises:[], sessions:[]}`. No automatic conversion, persistence or UI activation. Old v1 exports remain readable; v2 must fail closed in v1 apps. The legacy section retains every old record/configuration and existing IDs without re-keying or making a second persisted copy of individual logs.
- Separate plan definitions, actual session occurrences, exercise identity and sets. A session can reference a plan or have none. Stable new IDs are caller-supplied and checked for uniqueness; dates/names are not sufficient identities. Legacy sessions are grouped only by their existing date/template convention, explicitly labelled legacy. An explicit legacy extension can add occurrences or sets to that group without rewriting its legacy logs; overlapping set ordinals fail. Independent same-date sessions are distinct.
- Actual exercise identity is an exact existing plan/exercise reference or an explicitly chosen catalog ID. The optional planned slot is distinct from actual identity, so substitutions never inherit a movement's history or clearance merely by occupying its slot. No name-based links. Catalog muscle can be unknown. No automatic cross-plan equivalence; existing approved links retained, not applied to progression by this adapter. Future catalog mapping requires explicit approval per movement and unit.
- Only explicitly completed working sets or warmups enter this model. Actual kg/reps/RPE may be null, not filled from targets; explicit zero remains zero. Each load/repetition observation requires recorded or confirmed evidence for a numeric value, and unknown/planned/assumed evidence for null; the planned or assumed number stays in raw source evidence, not the actual field. Repetition unit is from the chosen identity; load basis is explicit or unknown. Legacy entered kg remains the entered number without assuming per-dumbbell, total, or stack basis. Extension of a legacy occurrence retains unknown load basis. Numeric strings already accepted by legacy validation are adapted read-only; missing legacy values remain unknown. No clinical clearance is inferred.
- Each set has one or more observations: first evidence, then explicit correction reasons and new evidence. CSV evidence carries a caller-supplied stable source identity, filename, record number and original record text. No personal fixtures in the public repository. Phase 2 must establish stable source/session IDs, explicit correction/apply rules (including how an audited correction overlays an immutable legacy observation), duplicate reconciliation against legacy rows and source preservation, not just accept arbitrary draft documents.
- Phase 1 provides pure validation and read-only normalization; it does not change current analytics, Train, import, reset, backup, or progression calculations. No v2 record can be saved or restored through the current v1 app. The v1 save path additionally refuses unsupported versions observed at write time (not an atomic cross-tab lock).

## Activation gates (subsequent work)

1. Implement reviewed import and a single version-aware persistence path, then switch **all** readers/writers together: Train, Dashboard, Strength Journey, logbook/CSV, volume/overlap, backup/restore (plain and encrypted), recovery inspection, reset, template transfer and any standalone workout-store consumer. Never silently omit new observations. Verify v1 restore and full v2 round trip, corrections, partial measurements, warmups, legitimate same-date sessions, explicit equivalences and clinical gates.
2. Resolve old cached/open-tab downgrade and concurrency risk before any v2 live write. A pre-existing old tab does not acquire the new guard; a version check is not a transaction. Prove stale saves cannot destroy v2 data; if the fixed-key localStorage design cannot guarantee that, stop for an explicit storage decision. Do not instruct clearing site data. Preserve recoverable original backup and establish a rollback path that never discards newer records.
3. Keep phase 1 and later phases reviewable, run native tests and preview asset check plus browser CI on final head. Device and real-data recovery acceptance remain separate; follow owner release gates before activation. No merge authorized by this implementation request.
