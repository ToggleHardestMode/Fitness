## Foundation contract

- One canonical workout-session representation: configuration (all original non-log fields), explicitly identified new catalog movements, independent actual sessions and performed occurrences. Legacy groups retain their original date/template convention; raw legacy rows and their original order/IDs are preserved once inside each canonical set. No permanent nested v1 document or legacy extension mechanism. The migration is pure, deterministic, and reconstructs the original v1 workout JSON semantically, including optional fields and numeric text. Legacy load and non-explicit repetition basis remain unknown. A new independent session can have extra sets, substitutions, per-side units or unknown measurements. No automated matching.
- Isolated native IndexedDB prototype with explicitly named fixture databases only; no live application imports, storage reads, or migration. A single validated snapshot and revision share a transaction. Expected revision 0 initializes an empty target; later commits require the expected current revision in the same readwrite transaction. Resolve only on transaction completion. Injected abort after put is used only for disposable failure tests. An append-only guard preserves original configuration and existing records; editor, audited corrections, source archive and import reconciliation are deferred. This is not a general-purpose production persistence API.
- A plain prototype backup envelope round-trips the canonical document; existing v1 JSON can initialize an empty fixture database. Original workout data remains recoverable separately. Compare the reconstructed v1 source with later legacy contents to flag divergence; never auto-import divergent legacy writes. Existing live plain/CSV and encrypted backups, Food Diary, reset, progression, and analytics are unchanged. The prototype does not yet implement encrypted v2 recovery or a two-store migration.
- Snapshot storage is intentionally the smallest transactional experiment. Before activation, measure five-year workloads on target browsers and decide whether individual session/object stores and indexes are necessary. Do not assume IndexedDB transactions protect against eviction, storage deletion, power loss or device loss. Independent verified backups remain required.
